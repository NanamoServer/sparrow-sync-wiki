## What travels with the player

Choose which data types to share: inventories, ender chests, experience, health, hunger, potion effects, advancements, statistics, attributes, location, and more. Each type has its own configuration switch.

<div className="sync-intro-highlights">
  <div>
    <strong>🔄 Smooth transfers</strong>
    <p>Most incoming data is prepared before the player joins, so they do not have to wait through a freeze after appearing in the world.</p>
  </div>
  <div>
    <strong>📦 Saved snapshots</strong>
    <p>Player data is stored as snapshots. Browse what was saved, inspect the contents, and restore an earlier record when needed.</p>
  </div>
  <div>
    <strong>🗺️ Shared maps</strong>
    <p>Map data can travel between servers too, with configurable synchronization modes and interaction controls.</p>
  </div>
</div>

Sparrow Sync uses Redis to coordinate player sessions across servers. For persistent snapshots, choose MongoDB, MySQL, MariaDB, or PostgreSQL. Player state is captured on the appropriate server thread; encoding and storage happen asynchronously, and work for the same player stays in order.

## Tools for administrators

Snapshots use Sparrow NBT and can be stored with Zstd or Deflate compression, or without compression. If something goes wrong, local exception archives and snapshot import, export, and bulk archive commands help you inspect and manage the data. You can also [migrate existing data](./migration) from HuskSync or InvSync with a command. See the [command reference](./commands) for the available tools.
